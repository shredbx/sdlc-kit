2. Repo filestructure

Three prior-art shapes exist already: this repo's own draft README.md (platform/ — "packages, frameworks, application bootstrappable templates and configured applications"), sbx-workspace (platform/python/{applications,frameworks,packages}, plus a separate projects/{products,experiments,prototypes,tools} and a top-level consumers/), and sbx.framework (packages/<name>/<lang>, apps/<name>/<lang>, projects/{bos,ide} as whitelabelable product instances, delivery explicitly out of scope). Your own message this turn — platform/python|go../packages|frameworks|apps, with products/experiments as their own scope — matches sbx-workspace's shape most closely, so that's what I've built the proposal around.

sdlc-kit/
├── processos.yaml
├── processos-workspace/              # process-os DEFINITIONS live here — see §3
│   ├── definitions/sbx-sdlc-kit/
│   ├── records/                       # kept in git — actual instances (e.g. a rendered app's spec)
│   ├── output/                        # git-ignored — per-run scratch only, NOT where real output lives

└── CLAUDE.md
Why platform/<lang>/apps/ and not straight into products/: an app under platform/ is a reusable, generic starter for that tech stack — cloneable, not tied to any one product. A product is what happens when one or more of those apps get combined with services, scripts, config, and content for an actual thing you're shipping. The Next.js starter is a platform/node/apps/ citizen; the AI Assistant product, once it exists, is a products/ citizen that uses that starter (and others) rather than copying them.
Decision needed apps (your wording this turn) vs. applications (sbx-workspace's actual folder name). I've used apps below, deferring to what you wrote just now — flag if you'd rather match sbx-workspace exactly.
Decision needed Nest products/ and experiments/ as siblings of platform/ (as drawn above — the most direct reading of "its own scope"), or nest them together under one parent the way sbx-workspace does (projects/{products,experiments,prototypes,tools})? The nested form groups "everything that isn't platform-native code" under one name, which may be worth it once prototypes/ or a tools/ equivalent shows up — but that's not a need yet, so I've defaulted to the flatter, current-need version.

3. process-os scope & namespace shape

One scope, sbx-sdlc-kit — not a separate scope per platform or per product yet. Splitting later (e.g. for independent readonly/readwrite boundaries) is cheap via uses: once there's a real reason; there isn't one yet.

Namespaces mirror platform/ directly: sbx-sdlc-kit.node, .go, .python, .swift, .kotlin — created one at a time, only when that platform is actually being worked. Within .node, framework (nextjs vs. sveltekit) is a typed field on the app schema, the same way process-os's own sdlc.application.framework is enum: [none, typer] within its python namespace — not a further folder split.

Decision needed The alternative to the paragraph above: namespace directly by framework (sbx-sdlc-kit.nextjs, .sveltekit) rather than by platform (sbx-sdlc-kit.node) with framework as a field. In practice almost every action, template, and package will be framework-specific anyway (a Next.js bootstrap script has nothing in common with a SvelteKit one), so the field-based grouping may just add a layer that never gets reused. I lean towards framework-level namespaces for that reason, opposite of what I assumed above — genuinely your call, this is exactly the kind of thing "precise, not ambiguous" should decide, not a default.

Reuse from process-os itself

Confirmed usable via a libraries: entry in processos.yaml (read-only, no fork): process-os's std scope (version, relative-path, file-list — genuinely generic, no reason to redefine). Not proposing to reuse sdlc/sdlc.python directly — they're process-os's own narrow demo content (python/typer only, hard-coded to that one framework choice in resolve-platform's shell script). Their shape — a generic dispatcher process that switches on a resolved platform into a platform-specific process — is worth copying; the rows themselves aren't reuse candidates.

4. The 13-capabilities question

You said: "I'd start with capabilities to and fulfill the processes looking at sbx v1 as reference." Last turn I flagged a real tension: sbx.framework tried capability-as- namespace and explicitly retired it (2026-08-01: "what a capability was becomes a subprocess"), after keeping that ruling for its entire 7.5-week build.

Resolved, 2026-09-24 — superseding the box below You meant it literally, and made the case well: capability is the outermost namespace (sdlc.<capability>.…), applied lazily — a path only gets created the moment a real definition needs it, never pre-scaffolded — which is what keeps this from repeating sbx.framework's "1000 capability files" failure while still getting the win it was actually for: process-cli list --namespace can answer "show me everything for this capability" as a real query. Ordering within a capability is action-first (e.g. sdlc.testing.documentation.…, not sdlc.documentation.testing.…) — confirmed in chat, not re-litigated here. Platform position (second-level vs. deeper) is still open, deliberately deferred until the types port gives us real content to test it against, per docs/proposals/porting-and-modeling-process.md.

5. Day-one starter set

Five definitions, each independently approvable, each existing only to get one real thing done: a Next.js app bootstrap matching bestays-web's confirmed environment (Next.js 15 + React 19, App Router + Turbopack, Tailwind v4, shadcn/ui "new-york", Radix, react-hook-form + zod, next-themes — docs/research/shredbx-bestierealestate-and-capabilities.md Part 3), minus its three @reactbook/* workspace-internal dependencies, which won't exist here.

Typesbx-sdlc-kit.node.app-name

A constrained string for an app's own name (kebab-case, filesystem- and npm-package-safe) — mirrors std.relative-path's style: a pattern with a comment showing a real example, nothing clever.

Schemasbx-sdlc-kit.node.app

Minimal: name, description, version (std.version), framework (start as a one-value enum: [nextjs] — add sveltekit the day that's real, not before). No platform/language split like upstream's — not needed until a second platform exists.

Templatesbx-sdlc-kit.node.nextjs-starter

The file tree itself: package.json (Next.js 15, React 19, Tailwind v4 via @tailwindcss/postcss, shadcn components.json pre-scaffolded "new-york"/neutral/lucide, react-hook-form+zod, next-themes), next.config.ts, app/ (App Router, no pages/), globals.css. A pattern: block (process-os's conform() mechanism) checking the load- bearing lines so drift from this baseline is detectable later, the same way process-os.package's own template does.

Actionsbx-sdlc-kit.node.create-nextjs-app

Shell action, type: shell: takes an sbx-sdlc-kit.node.app record, renders the template --into platform/node/apps/<name>, then pnpm install. A check.sh refuses to overwrite an existing app folder — same guard sdlc.python.create-project uses.

Processsbx-sdlc-kit.node.build-nextjs-app

One step today (create-nextjs-app) — kept as its own process rather than calling the action directly, so it's already shaped to grow a second step (e.g. an install- the-shared-chat-package step) without restructuring later. Not a speculative multi-step pipeline — a process of one real step is still a process, per process-os's own Process.of_action.

Deliberately not proposed yet: anything for the chat UI itself (that's the /experiments spike, explicitly process-free by your own instruction), anything for Go/Python/Swift/Kotlin, and any products/ definition — no product exists to compose yet.
